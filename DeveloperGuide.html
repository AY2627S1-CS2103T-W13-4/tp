Design

Architecture

The Architecture Diagram given above explains the high-level design of the App.

The following provides a quick overview of the main components and their interactions.

Main components of the architecture

Main (consisting of classes Main and MainApp) is in charge of the app launch and shut down.

  • At app launch, it initializes the other components in the correct sequence, and connects them up with each other.
  • At shut down, it shuts down the other components and invokes cleanup methods where necessary.

The bulk of the app's work is done by the following four components:

  • UI: The UI of the App.
  • Logic: The command executor.
  • Model: Holds the data of the App in memory.
  • Storage: Reads data from, and writes data to, the hard disk.

Commons represents a collection of classes used by multiple other components.

How the architecture components interact with each other

The Sequence Diagram below shows how the components interact with each other for the scenario where the user issues the command deletec 1.

Each of the four main components (also shown in the diagram above),

  • defines its API in an interface with the same name as the Component.
  • provides its functionality through a concrete {Component Name}Manager class that implements the corresponding API interface.

For example, the Logic component defines its API in Logic.java and implements it in LogicManager.java. Other components interact with a component through its interface rather than its concrete class, preventing them from coupling to that component's implementation, as illustrated in the following partial class diagram.

The sections below give more details of each component.

UI component

The API of this component is specified in Ui.java

The UI consists of a MainWindow and its parts, such as CommandBox, ResultDisplay, PersonListPanel, MeetingListPanel, and StatusBarFooter. The PersonListPanel and MeetingListPanel display clients and meetings respectively, using PersonCard and MeetingCard to represent individual entries. All of these, including MainWindow, inherit from the abstract UiPart class, which captures common behavior among classes that represent visible GUI parts.

The UI component uses the JavaFX UI framework. The layouts of these UI parts are defined in matching .fxml files in src/main/resources/view. For example, MainWindow.fxml specifies the layout of MainWindow.

The UI component,

  • executes user commands using the Logic component.
  • listens for changes to Model data so that the UI can be updated with the modified data.
  • keeps a reference to the Logic component, because the UI relies on the Logic to execute commands.
  • depends on classes in the Model component because it displays Person and Meeting objects from the model.

Logic component

API : Logic.java

How the Logic component works:

  1. When Logic is called upon to execute a command, the command text is passed to an AddressBookParser object, which creates a parser that matches the command (e.g., DeleteClientCommandParser) and uses it to parse the command.
  2. This results in a Command object (more precisely, an object of one of its subclasses e.g., DeleteClientCommand) which is executed by the LogicManager. Before executing the command, LogicManager checks whether the command is compatible with the currently displayed panel. For example, if the meetings panel is displayed, attempting to execute a client command such as deletec will result in a CommandException.
  3. The command can communicate with the Model when it is executed (e.g. to delete a person).
    Note that the code can require several interactions between the command object and the Model to complete the operation. For example, in the sequence diagram above, the command retrieves the filtered person list from Model, selects the person at the requested index, and then asks Model to delete that person.
  4. The result of the command execution is encapsulated as a CommandResult object which is returned from Logic.

How the parsing works:

  • When called upon to parse a user command, the AddressBookParser class creates an XYZCommandParser (XYZ is a placeholder for the specific command name, e.g., AddClientCommandParser). The parser uses the other classes shown above to parse the user command and create an XYZCommand object (e.g., AddClientCommand). The AddressBookParser returns that object as a Command object.
  • All XYZCommandParser classes, such as AddClientCommandParser and DeleteClientCommandParser, implement the Parser interface so they can be treated similarly where appropriate, for example during testing.

Model component

API : Model.java

Open the full-size model diagram

The Model component is implemented by ModelManager. It:

  • stores PingBook's clients and meetings in the AddressBook data class. Clients are represented by Person objects in a UniquePersonList, while meetings are represented by Meeting objects in a MeetingList.
  • represents each Meeting with a MeetingName, a MeetingDate, two MeetingTime values (startTime and endTime), and zero or more Tag objects.
  • exposes clients selected by the current filter through getFilteredPersonList() as an unmodifiable ObservableList<Person> view that the UI can observe.
  • maintains filteredMeetings, a FilteredList<Meeting> over the stored meeting list, and sortedMeetings, a SortedList<Meeting> over that filtered view. updateFilteredMeetingList(...) changes the filter, while updateMeetingListOrder(...) changes the display order without reordering stored meetings.
  • exposes sortedMeetings through getMeetingList() as an unmodifiable ObservableList<Meeting>. The UI receives this observable view through the Logic component and updates when its contents or order change.
  • stores a UserPrefs object that represents the user’s preferences (currently, just the GUI settings). This is exposed to the outside as a ReadOnlyUserPrefs object.
  • does not depend on any of the other three components (as the Model represents data entities of the domain, they should make sense on their own without depending on other components)

Storage component

API : Storage.java

The Storage component,

  • can save both address book data and user preference data in JSON format, and read them back into corresponding objects.
  • saves clients and meetings (including their tags) together in the address book JSON file, as the persons and meetings arrays. Data files without meetings or meeting tags still load.
  • is implemented by StorageManager, which delegates the actual JSON file access to JsonAddressBookStorage and JsonUserPrefsStorage (one class per data file).
  • depends on some classes in the Model component (because the Storage component's job is to save/retrieve objects that belong to the Model)

Common classes

Classes used by multiple components are in the seedu.address.commons package.

Appendix: Requirements

Product scope

Target user profile:

  • has a need to manage a significant number of contacts
  • prefers desktop apps over other types of applications
  • can type fast
  • prefers typing to mouse interactions
  • is reasonably comfortable using CLI apps

Value proposition: Secretaries have to juggle multiple contacts at once. These contacts are usually scattered across spreadsheets, notebooks, and memory. The app gives them a fast, reliable place to find the right contact in seconds.

Persona: Bob is a secretary at a fast-paced firm, supporting multiple department heads and sales leads. He is responsible for continuous schedule adjustments, external client contacts, and managing internal team members across projects. His client contact information and meeting schedules are scattered across messy spreadsheets and notebooks. Locating specific contact details or finding free calendar slots is inefficient and prone to error. As he is comfortable typing basic commands on a laptop, he wants a command-line interface application where all the information is stored.

Use cases

(For all use cases below, the System is the PingBook and the Actor is the user, unless specified otherwise)

Use case: UC1 - View and filter clients

MSS

  1. User requests to view clients, optionally providing one or more tags.
  2. PingBook displays the clients matching all supplied tags.

Use case ends.

Extensions

  • 1a. A supplied tag is invalid or empty.

    • 1a1. PingBook shows an error message.

      Use case ends.

Use case: UC2 - Add client

MSS

  1. User provides a name, phone number, email address, and optionally an address and tags.
  2. PingBook adds the new client.

Use case ends.

Extensions

  • 1a. A required field is missing or a supplied field is invalid.

    • 1a1. PingBook shows an error message.

      Use case ends.

  • 2a. The client already exists.

    • 2a1. PingBook shows an error message and does not add the client.

      Use case ends.

Use case: UC3 - Edit client

MSS

  1. User requests to edit a client using its displayed index and provides one or more fields to edit.
  2. PingBook replaces the supplied name, phone number, email address, address, or tags. A blank a/ or t/ removes the client's address or all tags instead.

Use case ends.

Extensions

  • 1a. The contacts panel is not active.

    • 1a1. PingBook shows an error message.

      Use case ends.

  • 1b. The index is invalid.

    • 1b1. PingBook shows an error message.

      Use case ends.

  • 1c. No field is provided, a supplied field is invalid (see "Field formats" in the User Guide), or a single-valued prefix is repeated.

    • 1c1. PingBook shows an error message.

      Use case ends.

  • 2a. The edited client duplicates another client.

    • 2a1. PingBook shows an error message and does not edit the client.

      Use case ends.

Use case: UC4 - Delete client

Extensions

  2. PingBook validates the meeting and saves it.

Extensions

Design notes

  • Two meetings overlap when they are on the same date and start < otherEnd && otherStart < end (Meeting#overlapsWith). Touching boundaries do not overlap. Finished meetings are included.
  • Model#getOverlappingMeetings(meeting, excluded) lists the overlaps; editm passes the meeting being edited as excluded so it is not compared with itself.
  • force/ is a valueless flag parsed by ParserUtil#parseForceFlag. Overlaps are computed on demand and never stored, so the JSON format is unchanged and saved files that already contain overlaps still load.

Non-Functional Requirements

  1. PingBook should run on Windows, macOS, and Linux with Java 25 installed, from a single JAR file without an installer or an internet connection.
  2. PingBook should support at least 1000 clients and 1000 meetings, with commands completing within 1 second under typical usage.
  3. A user with above average typing speed for regular English text (i.e. not code, not system admin commands) should be able to accomplish most of the tasks faster using commands than using the mouse.
  4. Client and meeting data should be stored in a human-editable text file.
  5. Client contact details and meeting information should remain on the user's computer. PingBook should not transmit them to a remote server or require an online account.
  6. All functions should remain usable at a screen resolution of 1280 × 720 with 150% scaling. At 1920 × 1080 with 100% or 125% scaling, controls and information should not overlap or be cut off.
  7. Command results, validation errors, and meeting status should be communicated in text, so users do not have to rely on colours or icons alone to understand them.

Glossary

  • Client: A person whose contact information are managed by the application
  • Meeting: A scheduled event with a name and time recorded by the application
  • Command alias: A user-defined alternative name or abbreviation for an application command

Appendix: Instructions for manual testing

Given below are instructions to test the app manually.

Note: These instructions only provide a starting point for testers to work on; testers are expected to do more exploratory testing.

Launch and shutdown

  1. Initial launch

    1. Prerequisite: Run PingBook in a folder without an existing data file.

    2. Test case: Launch the application.
      Expected: The GUI opens with the sample clients displayed.

  2. Saving window preferences

    1. Resize and move the window, then close and relaunch PingBook.
      Expected: The latest window size and position are restored.

Adding a client

  1. Adding a valid client

    1. Test case: addc n/Test Client p/91234567 e/test@example.com t/test
      Expected: The client is added and displayed with the supplied tag.

  2. Rejecting invalid or duplicate clients

    1. Test cases: addc n/Test Client p/invalid e/test@example.com, followed by the same valid addc command twice.
      Expected: Invalid data is rejected. The duplicate client is rejected and only one copy is stored.

Finding and filtering clients

  1. Filtering clients by tags

    1. Prerequisite: Add clients with different combinations of tags.

    2. Test case: listc t/friend t/colleague
      Expected: Only clients containing both tags are displayed. Tag matching is case-insensitive.

  2. Finding clients by name

    1. Prerequisite: Add clients whose names contain different keywords.

    2. Test case: findc alex david
      Expected: Clients matching either keyword are displayed, ignoring case.

Deleting a client

  1. Deleting a client while all clients are being shown

    1. Prerequisite: List all clients using the listc command, with multiple clients in the list.

    2. Test case: deletec 1
      Expected: The first client is deleted from the list. The status message shows the deleted client's details.

    3. Test cases: deletec 0, deletec, and deletec x
      Expected: No client is deleted. The status message shows error details.

Adding a meeting

  1. Validating and adding meetings

    1. Test cases: Add a valid meeting, then try a missing field, an invalid date, and an end time earlier than the start time.
      Expected: The valid meeting is added. Each invalid command is rejected with an error message.

  2. Detecting meeting overlaps

    1. Prerequisite: Add one meeting on a particular date.

    2. Test cases: Add an overlapping meeting without force/, then repeat it with force/.
      Expected: The first command is rejected with the conflicting meeting listed. The second command saves the meeting and displays a warning.

    3. Test case: Add a meeting that starts exactly when another meeting ends, without overlapping with any other meetings.
      Expected: The meeting is accepted because touching boundaries do not overlap.

Finding and filtering meetings

  1. Filtering and ordering meetings

    1. Prerequisite: Add meetings with different tags, including one whose end time has passed and one whose end time is in the future.

    2. Test cases: listm, listm t/work, and listm t/work t/urgent
      Expected: Meetings are filtered by all supplied tags. Meetings whose end time has not passed appear before meetings whose end time has passed.

Editing a meeting

  1. Editing a meeting

    1. Prerequisite: Display meetings using listm and ensure that the first meeting displayed does not overlap with other meetings.

    2. Test cases: editm 1 t/updated and editm 1 t/
      Expected: The first command replaces the meeting's tags and the second removes all tags.

Deleting a meeting

  1. Deleting a meeting while all meetings are being shown

    1. Prerequisite: List all meetings using the listm command, with multiple meetings in the list.

    2. Test case: deletem 1
      Expected: The first meeting is deleted from the list. The status message shows the deleted meeting's details.

    3. Test cases: deletem 0, deletem, and deletem x
      Expected: No meeting is deleted. The status message shows error details.
